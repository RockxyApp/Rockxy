# Block and Allow Lists

Block and allow lists solve a different problem from replay or rewriting. They help you control *which* traffic matters in the first place.

## Block List

Use Block List when you want matching requests to fail immediately instead of reaching the server.

Good candidates:

- analytics endpoints,
- ad and tracking SDK traffic,
- known-noisy background polling,
- third-party calls that distract from your main debugging session.

For GraphQL, set **GraphQL Operation** to block one operation (for example `DeleteUser`) while
every other operation on the same endpoint keeps working. Block rules created from a captured
GraphQL request prefill the operation name.

Set **Client Application** to block only what one app on this Mac sends, by name or bundle
identifier (for example `Safari` or `com.apple.Safari`). Requests from other apps are untouched.
The rule never matches traffic from another device, or from a process Rockxy could not identify,
so an unidentified caller is allowed rather than blocked.

## Allow List

Use Allow List when you want to restrict attention to a specific subset of traffic.

This is particularly helpful when:

- one app emits too much unrelated traffic,
- you want to focus on one service during capture,
- or you are validating that only a specific endpoint family is active.

Set **GraphQL Operation** on an Allow rule to record only one GraphQL operation from a shared
endpoint. Rules created from a captured GraphQL request prefill the operation name.

Set **Client Application** on an Allow rule to record only what one app on this Mac sends, by name or
bundle identifier (case-insensitive). Traffic from other devices, or from a process Rockxy could not
identify, does not match an application-scoped rule.

## When to choose which

- **Block List** removes traffic by making it fail.
- **Allow List** narrows the active traffic set to what you intentionally permit.
