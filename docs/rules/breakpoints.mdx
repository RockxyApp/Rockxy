# Breakpoints

Breakpoints let you stop a transaction at the proxy boundary and inspect or change the message that is already in flight. They are useful when the request is almost right, the backend cannot produce the state you need, or changing application code would make the debugging loop slower.

## Choose the phase

| Phase | Pause point | What you can change |
|---|---|---|
| **Request** | Before Rockxy connects to the origin | Method, HTTP host, path and query, headers, and text body |
| **Response** | After the origin replies but before Rockxy returns the response to the client | Status code, headers, and text body |
| **Request & Response** | At both points in the same transaction | Both message editors, one after the other |

For an HTTPS request, Rockxy keeps the established TLS authority fixed. You can still edit its path, query, headers, and body without creating a mismatch with the active connection.

## Create a rule

The fastest path starts from traffic you have already captured:

1. Select a transaction in the main request list.
2. Press `⌘B`, or choose **Add Breakpoint Rule** from the tools menu.
3. Give the rule a recognizable name.
4. Choose **Request**, **Response**, or both phases.
5. Review the prefilled method, URL pattern, match type, and path scope.
6. Press `⌘↩` to add the rule.

To author a rule without a captured transaction, open **Breakpoint Rules** with `⇧⌘B`, then press `⌘N`.

### Pause one GraphQL operation

GraphQL clients send every operation to the same endpoint, so a URL pattern alone pauses all
of them. Fill in **GraphQL Operation** to pause only requests whose operation name matches
exactly (names are case-sensitive). When you create the rule from a captured GraphQL request,
Rockxy prefills the operation name for you; clear the field to match every request to the URL.
Rockxy reads the name from the request's `operationName`, or from the document itself
(`query GetUser { … }`) when the client omits it. Anonymous operations never match a named rule.

## Resolve paused traffic

When an enabled rule matches, Rockxy opens the Breakpoint Queue. The main-window footer also shows how many transactions are waiting, so closing the queue never hides an active pause.

Choose one of three explicit outcomes:

- **Apply Changes & Continue** (`⌘↩`) rebuilds the message from the current editor and resumes the transaction.
- **Continue Original** discards the draft edits and resumes with the captured message.
- **Abort with 503** (`⌘.`) stops the transaction and returns `503 Service Unavailable` to the client.

`Esc` closes the queue without resolving anything. Use the orange queue indicator in the main-window footer to return to the waiting transactions.

Rockxy supports multiple paused transactions. Use `⌘[` and `⌘]` to move through the queue. Resolving one item does not change the draft or decision for the others.

## Edit safely

The structured tabs cover headers, body, query parameters, and the raw HTTP message. Before forwarding an edited message, Rockxy rebuilds its framing so the body length is not left stale.

If the captured body is not UTF-8 text, Rockxy protects the original bytes and disables body editing. You can still change request-line, status, or header fields without corrupting the payload.

## Verify the result

After the transaction completes, select it in the main request list. The inspector shows the final request and response that passed through Rockxy, along with the matched-rule impact. This makes it possible to compare what the origin produced with what the client actually received.

## Recovery behavior

- If the client closes its connection while traffic is paused, Rockxy removes that item from the queue and does not send it upstream later.
- Stopping the proxy releases all waiting items and clears the queue.
- Disabling a rule affects new traffic. It does not silently resolve a transaction that is already paused.

## Try a deterministic local example

The [live response debugging walkthrough](/use-cases/live-response-debugging-with-breakpoints) uses a localhost origin that always returns `plan: free`. A response breakpoint changes only the proxied result to `plan: pro`, then verifies continue-original, abort, and disabled-rule behavior.
